# SIH 2026 Problem Statement Report

## 1. Problem Statement Overview

- **Problem ID:** 26129
- **Problem Title:** Government Systems Interoperability Framework
- **Organization:** Ministry of Electronics and IT / Governance (Implied)
- **Category:** Software
- **Theme:** E-Governance
- **Difficulty Level:** Medium / Hard

### Problem Statement

> Government departments operate multiple independent portals and databases with different formats, authentication methods, and APIs. This prevents seamless information exchange, forcing citizens to submit the same info repeatedly and track applications across multiple offices. Officials lack a consolidated view. The challenge is to enable secure, standards-based interoperability without replacing existing systems.

### One-Line Summary

A centralized middleware "bridge" that allows different isolated government websites to securely share citizen data and logins with each other.

---

## 2. Problem Understanding

### What is the actual problem?

If you apply for a passport, the passport department doesn't talk to the police department or the electricity board. You have to submit your address proof and Aadhar everywhere. The government wants a secure backend system that connects all these legacy portals together so data flows seamlessly.

### Who faces this problem?

Citizens (wasting time), Government officials (duplicate verification work), and IT admins.

### Why is this problem important?

It is the core of modern e-governance (like India Stack / X-Road in Estonia). It saves millions of man-hours.

### Existing Problems / Limitations

Current systems are built by different vendors using different databases, languages, and security protocols. They are silos.

---

## 3. Expected Solution

### What is SIH asking us to build?

An interoperability framework (middleware/API Gateway). It should feature:
1. API-based data exchange.
2. Consent-based data sharing (Citizen approves sharing their data from Portal A to Portal B).
3. Single Sign-On (SSO).
4. Unified application tracking.
5. Audit logs and role-based access.

### Proposed Solution Concept

An API Gateway (using Kong or custom Node.js) acting as a central hub. We build 3 "Dummy" government portals (e.g., Portal A: RTO, Portal B: Passport, Portal C: Tax). We implement an OAuth2.0 SSO so logging into one logs into all. We implement a consent manager so if Portal B requests address data from Portal A, the user gets an OTP to approve it.

### Key Features

- Single Sign-On (SSO) identity provider.
- Consent-based data exchange API.
- Dashboard for citizens to track their applications across all departments.
- Reusable connectors for legacy systems (e.g., SOAP to REST conversion).

## 8. MVP Feasibility for SIH

### Can we build an MVP during the hackathon?

**Verdict:** Yes

### MVP Scope

Build an Identity Hub and 2 mock department portals. Show a user logging into Hub, getting an access token, going to Portal A, filling a form. Then the user goes to Portal B, hits "Import Data", a consent popup appears, they click yes, and Portal B pulls data securely from Portal A via the central Gateway.

### What should NOT be attempted during the hackathon?

- Integrating with actual live government APIs (like real Aadhar).

### Estimated Development Difficulty
